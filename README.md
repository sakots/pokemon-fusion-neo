# pokemon-fusion-neo

[ポケナビのポケモンフュージョンジェネレーター](https://pknavi.com/pokemonfusiongenerator)を参考に、全国図鑑No.0001〜1025のポケモンを合体できる生成機を開発するプロジェクトです。

現在は調査・設計段階です。アプリケーション、データ、合成処理、テストはまだ実装していません。

## 元サイトの仕組み

2026/10/13にHTML、公開JavaScript、合体画像1枚を確認しました。

### 確認できたこと

- 画面はReactで実装され、ジェネレーターのコードは別のJavaScriptファイルとして読み込まれます。
- ジェネレーターの選択用データは386件です。全国図鑑No.0001〜0386で、名前、図鑑番号、世代、合体名の前半・後半を持ちます。
- 左右のポケモンの選択、名前検索、ランダム選択、左右交換があります。
- 合体画像は、左の世代・図鑑番号と右の図鑑番号から次のURLを組み立てて、`img`要素で表示します。

```text
https://images.pknavi.com/fusionPokemon/{左の世代}/{左の番号}/{左の番号}-{右の番号}.png
```

- 元のポケモンの画像も、`basePokemon/{世代}/{番号}.png`から取得します。
- 合体名は左の`leftName`と右の`rightName`を連結します。同じ番号同士なら元の名前を表示します。
- ジェネレーターのコードにはCanvasによる画像合成や、画像生成APIの呼び出しはありません。
- `gen1/0001/0001-0004.png`はHTTP 200で取得でき、53×83ピクセルのPNGでした。キャッシュと最終更新日時のヘッダーもあり、用意済み画像の配信と整合します。

つまり、確認できたブラウザ側の仕組みは「合体結果の画像URLを選んで表示する」方式です。選択時にブラウザで顔や体を切り貼りしているわけではありません。

### まだ分からないこと

- 配信されるPNGを作成したプログラム、制作手順、素材の出典。
- 手描き、画像処理による自動生成、個別修正がそれぞれどの程度使われているか。
- 全386×386通りの画像が存在するか。今回は1枚のみ確認しています。
- 配信サーバー内部の実装。公開コードとレスポンスだけでは、画像の事前生成を断定できません。

見た目から頭・体・配色の組み合わせを推測できても、それを元サイトの生成アルゴリズムとして断定しません。

## 1025種類への拡張方針

対象は全国図鑑No.0001〜1025の種ごとの基本形とします。リージョンフォーム、メガシンカ、姿違い、色違いは初期対象に含めない設計案です。

左右を区別し、同種同士を含めると、1025×1025＝1,050,625通りになります。異なる種同士だけでも1,049,600通りです。選択用データを増やすだけでは、その組み合わせの合体画像は得られません。

| 方式 | 必要なもの | 課題 |
| --- | --- | --- |
| 用意済みPNGを表示 | 各組み合わせの完成画像と配信先 | 約105万通りの画像を作る工程が必要。画質と容量は制作方式に依存する |
| 選択時に画像を合成 | 各種の素材、部位マスク、接続位置、配色情報、合成処理 | 各種の形状に合わせた準備と、組み合わせ時の品質確認が必要 |

最初に検証する案は、**各種の部位情報を用意し、ブラウザのCanvasで選択時に合成する方式**です。完成画像を全通り持つ必要がなく、静的サイトとして構成できます。ただし、元サイトと同じ画質を保証する方式ではありません。

合成処理は次の流れを想定します。

1. 左のポケモンを頭、右のポケモンを体として扱う。
2. 素材ごとのマスクで頭を切り出し、体素材の元の頭を除去する。除去跡に必要な補完素材も用意する。
3. 接続位置と倍率を使って頭を体に配置する。ドット絵なら拡大縮小時の補間を無効にする。
4. 必要に応じて体の色を頭側の配色へ寄せる。輪郭、目、模様まで一律に置換しないよう領域を分ける。
5. 合体名を組み立て、画像と一緒に表示する。同種同士は元画像・元の名前を返す設計案とする。

画像の上半分と下半分を一定の高さで切り貼りするだけでは、首の位置、角度、大きさが揃いません。頭と体が一体の種、複数の頭を持つ種、蛇型などは、個別のマスクや接続方法が必要です。素材を1025枚集めることと、1025種類の合成に対応することは別の作業です。

## データと素材の候補

- 日本語名、世代、種と姿違いの区別には[PokéAPIのPokemon Species](https://pokeapi.co/docs/v2#pokemon-species)を候補とします。基本形は`varieties`の`is_default`で確認します。
- 画像は[PokeAPI/sprites](https://github.com/PokeAPI/sprites)を候補とします。ゲーム由来の画像とコミュニティ制作の画像があり、サイズ・画風も複数あります。
- リポジトリが第9世代の画像を扱っていても、採用する同一系列でNo.0001〜1025が揃うかは別途検証します。欠落、透過、寸法、画風、素材の利用条件を確認してから系列を決めます。
- データは準備時に取得・検証し、アプリ用データとして保存する案です。画面を開くたびに1025件のAPIを呼びません。PokéAPIの利用方針も取得データのローカルキャッシュを求めています。
- 合体名の分割位置と、画像の部位情報はPokéAPIにはないため、独自に定義する必要があります。

## 次の開発単位

AGENTS.mdに従い、各段階で資料更新 → テスト → 最小実装 → 不要コード・資料矛盾の確認を行います。

1. 画風と画像系列を決め、1025種類のデータ・画像の欠落を検証する。
2. 形状の異なる少数の種で、頭と体の切り出し・接続・配色を試す。ドット絵として成立するか目視確認する。
3. 合成規則を資料に定義し、透過、接続座標、左右交換、同種同士、範囲外番号の動作をテストしてから実装する。
4. 全種の部位データを整備する。対象数だけで完了とせず、各種の素材・部位データの検証と、形状別の合成品質確認を行う。
5. 検索、ランダム、左右交換を持つ画面に接続する。リリース前にテスト・テーマ診断・差分チェックを通す。テーマ診断の具体的な手順は画面実装時に定義する。
